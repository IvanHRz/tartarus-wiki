# Plan — Cierre de los pendientes del audit: sensores, cebos y correlación (TARTARUS)

## Context

Tras cerrar las tres olas del audit de falsos positivos (ya en GitHub, commit `707f7a2`), quedaron
pendientes los hallazgos de segundo orden que la auditoría destapó pero no corrigió. Tres agentes
exploraron el código y confirmaron que varios son **bugs reales**, no solo pulido:

- El sensor ICMP se reporta **`failed` en el despliegue** (el usuario lo vio en pantalla) **y `offline`
  para siempre** en el panel, aunque funcione: se le hace una sonda TCP a `icmp-canary:8000` (puerto que
  en realidad es del *engine*; el sensor no escucha ningún socket) y nadie emite nunca su heartbeat.
- El health worker abre **~14.400 conexiones/día contra los puertos de ataque** de Beelzebub. Es el
  origen del ruido que hoy solo filtramos en la ingesta; el contador de Beelzebub sigue inflado.
- **OpenCanary marca todo evento como cebo disparado** (`canary_triggered=True`), saltándose la puerta de
  interacción real que añadimos: con la config activa (FTP/SMB/MySQL/RDP/SNMP), cada conexión de un
  escaneo manda correo.
- El **web-bug** de los documentos-cebo dispara con previsualizadores de enlaces (Outlook Safe Links,
  Slack, antivirus) y atribuye la IP del proxy; captura el `user-agent` pero nunca lo mira.
- El detector de **port-scan no es una ventana deslizante real** (el `EXPIRE` se rearma en cada evento →
  un escáner lento acumula para siempre) y no tiene exención para un escáner corporativo legítimo.
- Las **reglas Sigma de umbral** (`event_count`) siguen desactivadas: el fix de la Ola 1 fue saltarlas.

Decisiones del usuario: (1) salud de sensores → **híbrido** (métricas como señal principal + sonda TCP
espaciada); (2) OpenCanary → **solo alerta el intento real** (login/credencial), las conexiones se
registran sin correo.

Rama `feature/tier0-deployment-readiness`. Suite actual **1066 verde**. Regla: suite verde y verificación
en vivo al cerrar cada ola (stack local, engine en `:9001`).

## OLA A — Sensores: lo que el usuario ve en pantalla

**A.1 Sensor ICMP: dejar de verificarlo con una sonda TCP** — `engine/engine/sensor_manager.py:43`
(`_SensorEndpoint("icmp", "icmp-canary", 8000)`). El `:8000` es el puerto del *engine*, y el contenedor
`icmp-canary` no publica ni escucha nada (`docker-compose.yml:176-194`, solo `cap_add: NET_RAW`) → la
sonda **nunca** puede tener éxito. Añadir un modo al endpoint (`mode: "probe" | "push"`) y, para
push-mode, verificar por estado real en vez de socket. `deploy_sensors` no recibe pool hoy, pero
`deploy_router.py:152-155` sí lo tiene en scope: pasarlo. Nuevo estado `registered`/`push_mode` en la
tabla de resultados para que la UI no pinte rojo (el test de deploy solo asserta sobre la clave `http`,
así que cambiar `icmp` es barato).

**A.2 Cerrar la brecha del heartbeat (bug latente: `offline` perpetuo)** —
`engine/engine/icmpcanary_router.py:154-166` inserta el evento con `honeypot_id = ev.sensor_id`, que
coincide con la PK de `sensor_registry`. Estampar ahí mismo `last_heartbeat`/`status` con un UPSERT
ligero (no requiere tocar la imagen del sensor ni redesplegar contenedores de campo). Con eso
`_classify_status` deja de caer en la rama "sin heartbeat → offline" (`sensor_health_worker.py:97-98`).
Mismo tratamiento para el webhook de sensores de campo si aplica (`ingest_router.py`).

**A.3 Health worker híbrido (menos ruido en origen)** — `engine/engine/sensor_health_worker.py:119-127`.
Para `sensor_type == "beelzebub"`: señal principal = **métricas Prometheus reales** (`:2112`, puerto que
NO es honeypot), reusando `BEELZEBUB_METRICS_URL` y `parse_beelzebub_metrics` de
`observability_router.py:33,52` — una petición por pasada cubre las 5 filas. La **sonda TCP se conserva
pero espaciada** (cada N pasadas, ~5 min, configurable por env) para no perder la granularidad
puerto-a-puerto. Reduce el ruido ~90% conservando el detalle.
Además: `_PUSH_TYPES` (`:44`) es documentación muerta (la decisión real es `in _PROBE_TYPES and port is
not None`) y `sensor_type` no se usa dentro de `_classify_status` (`:69`) — limpiar sin cambiar la
semántica que fijan los tests.

**Cuidado con los tests**: `engine/tests/unit/test_sensor_health_worker.py` parchea
`engine.sensor_health_worker._probe_tcp` **por ruta de string** → conservar ese símbolo y su firma; y
exige que los sensores push no se sondeen nunca.

**Verificación A:** suite verde; reiniciar engine; en la UI el sensor ICMP aparece **activo** (no
offline) y el despliegue ya no dice "failed" para ICMP; contar en el log/BD que las conexiones a los
puertos de ataque bajan (comparar `beelzebub_*_events_total` antes/después de 5 min); test nuevo de
`_classify_status` para push-mode con heartbeat estampado por el webhook.

## OLA B — Cebos: que solo avise lo que importa

**B.1 OpenCanary: alertar solo el intento real** — `engine/engine/opencanary_router.py:132`
(`canary_triggered = True` incondicional) + `:152-157` (`notifier.send` sin umbral). La distinción ya
existe **en las descripciones** de `LOGTYPE_MAP:27-50`: login/credencial (5000 FTP login, 4000 SSH login,
3001 HTTP POST login, 12001 MySQL login, 6001 Telnet login, 11001 SNMP community, 8001 SMB file open) vs
conexión/scan (5001 FTP connection, 4002 SSH connection, 3000 HTTP GET, 8002 SMB tree connect, 14001 RDP
connection, 11000 NTP monlist). Añadir un **conjunto de logtypes de alto valor** (no cambiar la aridad de
la tupla: `test_opencanary.py` desempaqueta 3 elementos) y marcar `canary_triggered` solo para esos; el
resto se registra igual (evento + detección) pero pasa por el umbral normal. Reusar el precedente de
`icmpcanary_router.py:180`. Señal extra ya disponible y hoy ignorada: `logdata.USERNAME`/`PASSWORD`.

**B.2 Web-bug: distinguir previsualizadores de una apertura real** —
`engine/engine/canary_router.py:572-704`.
- **Heurística de user-agent**: `user_agent` se captura (`:586`) y se desecha analíticamente. Añadir una
  lista de previsualizadores/unfurlers (Safe Links / `SkypeUriPreview`, `Slackbot-LinkExpanding`,
  `Slack-ImgProxy`, `BingPreview`, `facebookexternalhit`, `WhatsApp`, `Twitterbot`, `Mimecast`,
  `Proofpoint`, `Barracuda`, `curl/`, `python-requests`, `Go-http-client`, `HeadlessChrome`). No existe
  ninguna lista así en el repo (las de `risk_engine.py:265` y `suspicious_user_agent.yml` son de
  escáneres ofensivos, otra cosa).
- **Marcar, no descartar**: el disparo se sigue registrando (es evidencia) pero con
  `tags = ['PREVIEWER_SUSPECTED']` y sin alertar. `events.tags TEXT[]` ya existe (`db/init.sql:22`) y
  `notifier.should_alert` ya inspecciona `tags` (`notifier.py:345`) → **cero migración de esquema**.
- **IP real del visitante**: hoy se toma el **primer** elemento de `X-Forwarded-For` (`:581-585`), que es
  spoofable y además devuelve la IP del proxy previsualizador. Con el nginx del proyecto
  (`ui/nginx.conf:17-18`: `X-Real-IP = $remote_addr`, XFF = `$proxy_add_x_forwarded_for`) el **último**
  elemento es el peer real. Cambiar a `X-Real-IP` / último salto, **conservando el XFF completo en el
  payload como evidencia** y con un knob de configuración (nº de saltos de confianza) para el escenario
  off-site vía Cloudflare Tunnel. Ojo: `test_canary_webbug_http.py:100-105` fija hoy el comportamiento
  del primer elemento — hay que actualizarlo conscientemente (codifica la vulnerabilidad).
- Documentar el hueco en `docs/CEBOS_QUE_DISPARAN.md` (hoy afirma que el web bug es "✅ Siempre (los más
  fiables)", justo lo que el previsualizador rompe).

**Cuidado con los tests**: `test_canary_fire_matrix.py:144-154` y `test_notification_dispatch.py:53-56`
fijan por contrato "canary_triggered siempre alerta" — se actualizan a la nueva semántica (un cebo
**real** sigue alertando siempre; lo que cambia es quién se marca como cebo real).

**Verificación B:** suite verde; disparar el web-bug con un UA de previsualizador (`curl -H
'User-Agent: Slackbot-LinkExpanding 1.0'`) → evento registrado con la etiqueta y **sin** correo; con un
UA de Word → alerta normal; POST de OpenCanary con logtype 14001 (RDP connection) → sin correo, con
logtype 5000 (FTP login) → correo.

## OLA C — Port-scan y correlación real

**C.1 Ventana deslizante de verdad + exención de escáner conocido** —
`engine/engine/portscan_detector.py:33-37` usa `SADD` + `EXPIRE` rearmado en cada evento → bajo tráfico
continuo la llave nunca expira y el set crece indefinidamente ("300 s de inactividad", no ventana).
Migrar al patrón **ZSET con score = timestamp** que ya usan `rate_limiter.py:44-71` y
`kill_chain_tracer.py:82-97` (`zadd` / `zremrangebyscore` por cutoff / `zcard`), en un `pipeline()` para
1 RTT. Añadir **allowlist de escáneres autorizados** (env con IPs/CIDRs, reusando el parser de
`infra_filter.py:60-79` que ya entiende CIDR): el evento se registra y la detección se anota, pero **sin
el bump a 75 ni notificación** — hoy no existe el punto medio entre "descartar el evento entero"
(`infra_filter`) y "silenciar solo el correo" (`ignored_ips`).
Nota: `test_portscan_detector.py:7-30` trae un `FakeRedis` sin `zadd`/`zcard` → hay que extenderlo (y la
fixture `mock_redis` de `conftest.py:122-137` tampoco los tiene).

**C.2 Correlación real para las reglas de umbral** — reactivar lo que la Ola 1 dejó apagado.
`sigma_lite.py:211-215` marca `requires_correlation` pero **descarta los metadatos** (`pop` de
`correlation`/`timeframe`): primero hay que **conservarlos** (`type`, `group-by`, `timespan`,
`condition.gte`). Implementar solo `type: event_count` (los 7 del corpus son de ese tipo) reusando el
ZSET de `kill_chain_tracer.py:82-97`, que da además `first_seen`/`last_seen` para `matched_fields`, y el
candado "una vez por ventana" (`SET NX EX`) de `portscan_detector.py:45`.
**Punto de enganche**: el bucle async `consume_events` (`consumer.py:511`), junto al bloque de portscan
(`consumer.py:602-628`) — `_parse_event` es **síncrono** y no recibe redis, así que ahí no se puede.
**Alcance real**: de las 7 reglas con correlación solo **2 llegan al motor** (`ssh_brute_force`, high,
gte 5 en 5m; `icmp_ping_sweep`, medium, gte 3 en 30s); las otras 5 las filtra la aplicabilidad por usar
campos EDR. Y `icmp_ping_sweep` tiene **dos bloqueos extra** que hay que resolver o dejar anotados: el
ingest ICMP no ejecuta Sigma en absoluto (`icmpcanary_router.py:106-189`), y la regla pide
`command|contains: 'Echo request'` mientras el comando real es `ICMP:echo_request_received` (guion bajo
vs espacio). → En la práctica esta ola reactiva **ssh_brute_force** y deja el camino hecho para el resto.

**Verificación C:** suite verde; un solo intento SSH fallido **no** dispara brute-force, cinco en 5 min
**sí** (y una sola vez por ventana); un escaneo de 10 puertos desde una IP de la allowlist se registra sin
subir a 75 ni notificar; test de expiración real de la ventana (evento viejo fuera del ZSET).

# Plan — Limpieza de los datos-ruido (purga histórica + flocks de prueba)

## Context

Es el punto 1 de los pendientes: la única parte del audit de falsos positivos que quedó sin ejecutar.
El código ya no ingiere ruido (el filtro de infraestructura corta en la ingesta desde el 25-ago), pero la
base **todavía arrastra lo que entró antes del arreglo**: los eventos que generaba el propio stack (el
health worker sondeando los puertos de ataque, las verificaciones de despliegue, Beelzebub contra sí
mismo). Mientras sigan ahí, los paneles, los informes y el conteo del flock cuentan ruido como si fueran
ataques.

Estado medido ahora mismo:

| Concepto | Ahora | Tras la limpieza |
|---|---|---|
| Eventos | 3720 | **1392** |
| Detecciones | 15978 | **6681** |
| Eventos de infraestructura (a borrar) | 2328 | 0 |
| Gateway `.1` (simulaciones reales, se conservan) | 1389 | 1389 |

La operación **es destructiva e irreversible**, y el clasificador del harness ya la bloqueó dos veces por
eso. Este plan la ejecuta con red de seguridad y verificación, no a pelo.

### Lo que se comprobó antes de planear (todo medido, no supuesto)

- **Las IPs de los contenedores rotaron** entre reinicios (hoy `.7` es postgres y Beelzebub es `.11`). No
  afecta: el script borra por *subred menos gateway*, no por IPs concretas.
- Los 2328 eventos arrastran **9297 detecciones** (el corpus Sigma sobre-emparejado de antes generaba ~4
  por evento). El script ya las contempla.
- **Único hueco real del script**: `kill_chain_traces.event_ids` es un **array sin clave foránea** y hay
  **1 traza** que referencia eventos a borrar → quedaría con ids colgando.
- **Riesgos que resultaron ser cero hoy** (verificados uno por uno, se dejan cubiertos igual por si
  cambian): `mitre_evidence` está **vacía** (0 filas → no puede abortar la transacción por su FK a
  `detections`, que era el riesgo más serio); `activity_clusters` **vacía**; **0** `correlation_sessions`
  de IPs internas.
- `AUDIT_A` y `AUDIT_B` están **completamente limpios**: 0 eventos, 0 cebos, 0 detecciones, 0 trazas, 0
  sesiones, 0 honey-creds. Borrarlos no arrastra ni re-hospeda nada.
- **No hay mecanismo de respaldo**: `backups/` solo tiene dos volcados manuales del 3-may-2026 y el
  Makefile no tiene target de dump. La BD pesa **21 MB** → un `pg_dump` es cuestión de segundos.
- Sobreviven **3 eventos sintéticos de mis pruebas de hoy** (`198.51.100.5` RDP, `198.51.100.6` FTP,
  `203.0.113.77` ICMP): están fuera de la subred interna.

## Paso 1 — Red de seguridad: respaldo antes de tocar nada

No hay convención de respaldo, así que se crea una: `pg_dump` comprimido a
`backups/db/tartarus_YYYYMMDD_HHMM.sql.gz`. Se **verifica** que el fichero pese > 0 y contenga
`COPY public.events` **antes** de borrar nada. Se añade `backups/db/` al `.gitignore` (un volcado lleva
datos de clientes: no debe subirse) y se deja el comando de restauración escrito en el propio script y en
el ROADMAP, que hoy no existe en ninguna parte.

## Paso 2 — Tapar el hueco de `kill_chain_traces` en el script

`scripts/purge_infra_noise.sh` borra `detections` y `mitre_evidence` (las dos FK reales) pero no toca los
arrays sin FK. Añadir, **dentro de la misma transacción**: quitar de `kill_chain_traces.event_ids` los ids
borrados y eliminar la traza si se queda sin eventos. Hacer lo propio con `activity_clusters` (hoy vacía,
pero el script debe quedar correcto). Es 1 traza ahora; el objetivo es que el script sirva la próxima vez.

## Paso 3 — Ejecutar la purga

Correr primero el **dry-run** para confirmar el alcance en ese momento, y después
`./scripts/purge_infra_noise.sh --apply` (ya es transaccional: `BEGIN … COMMIT` con `ON_ERROR_STOP=1`, y
borra en orden dependientes → eventos).

**Si el clasificador vuelve a bloquear el borrado, no se fuerza ni se rodea**: se deja el respaldo hecho y
el script listo, y se le pasa a Iván la única línea que tiene que correr.

## Paso 4 — Flocks de prueba y eventos sintéticos

- Borrar `AUDIT_A` y `AUDIT_B` con `DELETE /flocks/{id}` (vía API, no SQL, para respetar la lógica del
  endpoint). Están vacíos, así que el re-hospedaje al Default que hace ese endpoint no mueve nada — que
  era justo el riesgo a evitar. **No** se toca el flock `Iván` (es real).
- Borrar los 3 eventos sintéticos de mis pruebas, para que no ensucien informes. Se identifican por sus
  rangos de documentación (`198.51.100.0/24`, `203.0.113.0/24`, reservados por RFC 5737 para ejemplos), no
  por fecha, para no arrastrar nada legítimo.

## Paso 5 — Reconciliar los contadores

`consumer:events_total` en Redis **nunca se decrementa** al borrar. Tras la purga, el embudo de
`GET /observability/reconcile` compararía ~3700 ingeridos contra 1392 persistidos y cantaría una **pérdida
de escritura falsa** (justo el tipo de dato engañoso que este audit viene arreglando). Se descuenta lo
purgado de `consumer:events_total` y de `consumer:events_by_proto:*`, y se comprueba que el embudo vuelva
a 0 % de pérdida real.

## Verificación
1. El respaldo existe, pesa > 0 y contiene `COPY public.events`.
2. Conteos reales: eventos **1392**, detecciones **6681**, **0** eventos con IP de contenedor (subred
   menos `.1`), y los **1389** del gateway intactos.
3. Ninguna traza de kill-chain referencia eventos inexistentes (consulta de huérfanos = 0).
4. `AUDIT_A`/`AUDIT_B` ya no salen en `GET /flocks`; `Default Flock` e `Iván` sí.
5. El embudo `GET /observability/reconcile` no reporta pérdida falsa.
6. La UI carga y el flock muestra los números nuevos (`event_count` y `event_count_24h`); `GET /health`
   sigue `ok`; la suite (**1090**) sigue verde — la purga no toca código de negocio, pero el script sí
   cambia, así que se corre igual.
