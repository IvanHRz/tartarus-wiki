# Plan — Telnet nativo + HTTPS/TLS nativo (habilitados por Beelzebub v3.9.0)

## Context

El upgrade a Beelzebub v3.9.0 desbloqueó **telnet nativo** y **TLS/HTTPS nativo**; el usuario eligió
construir ambos (son config, no build, y cierran dos huecos de cobertura). **Telnet nativo** cierra el
hallazgo del análisis (`docs/ANALISIS_TELNET.md`): hoy el honeypot de :23 habla SSH y **no captura telnet
crudo/IoT (Mirai)**. **HTTPS nativo** cierra el hueco del estudio (`docs/ESTUDIO_HTTPS_TLS.md`): el :8443
está mapeado sin servicio (cobertura falsa) y da paridad con Thinkst.

Hallazgos verificados (schema embebido en el binario v3.9.0 + config local):
- **Protocolo `telnet` es nativo** (enum `["ssh","http","tcp","telnet","mcp"]`) y comparte struct con los
  demás → soporta `commands` + `plugin` → el telnet nativo puede llevar **LLM Cisco + respaldo estático +
  guardrails** (lo que ya tenemos en `telnet-23.yaml`).
- **TLS = `tlsCertPath` + `tlsKeyPath`** (rutas a archivos, ambos obligatorios; Go verifica existencia al
  arrancar). Los configs se montan read-only en `/configurations` (`docker-compose.yml:15`) → el cert va en
  `beelzebub/configurations/certs/` y se referencia como `/configurations/certs/...`.
- **:443** ya está mapeado en `docker-compose.dev-mac.yml:7` (`8443:443`) pero NO en el compose base ni en
  el contenedor actual → añadirlo al base como puerto de honeypot de primera clase.
- **consumer** (`consumer.py`): `_PORT_PROTOCOL_MAP` ya mapea `23→TELNET`; deriva `dest_port` del
  `ServerAddr`. Los eventos de :443 quedarán como `HTTP` con `dest_port=443` (aceptable; etiqueta HTTPS
  explícita queda como follow-up opcional, sin tocar el pipeline ahora).

## Decisiones (tomadas, alineadas con el alcance)
1. **Convertir :23 a telnet nativo** (`protocol: ssh` → `protocol: telnet`), conservando el CLI Cisco por
   LLM + respaldo estático + guardrails. El puerto telnet ahora habla telnet (lo correcto). Se pierde el
   acceso por SSH al Cisco (workaround previo); si más adelante se quiere, se añade un Cisco-SSH en otro
   puerto. `:22` (Ubuntu SSH) no se toca.
2. **HTTPS con certificado autofirmado** (configurable: la ruta permite sustituirlo por uno de CA real),
   sirviendo el mismo portal que `http-80`. Autofirmado es lo estándar para un honeypot.
3. **:443 como puerto de honeypot de primera clase** en el compose base.

## Pasos

### A. Telnet nativo (`beelzebub/configurations/services/telnet-23.yaml`, gitignored)
- Cambiar `protocol: "ssh"` → `protocol: "telnet"`. Mantener `commands` (handlers Cisco estáticos + catch-all
  `plugin: LLMHoneypot`), `serverVersion`, `passwordRegex`, bloque `plugin` (LLM + prompt con guardrails).
- Restart Beelzebub. **Verificar**: `telnet`/`nc localhost 2323` → login + `show version` (estático) +
  comando raro (LLM) + intento de jailbreak (guardrail sigue en personaje); eventos llegan como **TELNET**.
  (El test por SSH ya no aplica: ahora es telnet de verdad.)
- Si el LLM no se comporta bien sobre telnet nativo → dejar telnet estático (aún captura y responde a los
  top) y anotar; no bloquea.

### B. HTTPS/TLS nativo
- **Certificado autofirmado:** generar `cert.pem`/`key.pem` en `beelzebub/configurations/certs/` (CN
  plausible, p.ej. el hostname interno). `openssl req -x509 -newkey rsa:2048 -nodes -days 825 …`.
- **Servicio nuevo** `beelzebub/configurations/services/https-443.yaml` (gitignored): `protocol: "http"`,
  `address: ":443"`, `tlsCertPath: /configurations/certs/cert.pem`, `tlsKeyPath: /configurations/certs/key.pem`,
  `commands` = clon del portal de `http-80.yaml` (mismo contenido, ahora sobre TLS).
- **Puerto:** añadir `- "${HTTPS_PORT:-8443}:443"` a los `ports` de beelzebub en `docker-compose.yml` (base).
- Recreate beelzebub (con el mapeo :443). **Verificar**: `curl -k https://localhost:8443/` → 200 con el
  portal; handshake TLS OK con el cert; el evento aterriza (protocol HTTP, `dest_port=443`).

### C. Higiene + scripts + ejemplos
- **`.gitignore`:** añadir `beelzebub/configurations/certs/` (la clave privada nunca se versiona).
- **`scripts/attack_all.py::attack_telnet`:** ahora que :23 es telnet nativo, volver a ataque telnet crudo
  (socket/`nc`-style, como el original) en vez de SSH; verificar que produce eventos TELNET. `attack_https`
  ya apunta a :8443 (ahora sí responde) — verificar.
- **`beelzebub/configurations/services.example/`** (tracked): actualizar `telnet-23.yaml` a `protocol: telnet`
  y añadir un `https-443.yaml` de ejemplo (con rutas de cert de placeholder) para que el patrón quede
